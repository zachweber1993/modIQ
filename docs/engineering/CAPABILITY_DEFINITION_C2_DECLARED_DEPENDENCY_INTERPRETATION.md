## Repository Context

`docs/engineering/PLATFORM_FOUNDATION_V1_DECLARATION.md` and `docs/engineering/POST_FOUNDATION_ENGINEERING_CAPABILITY_ASSESSMENT.md` are treated as settled, per `PROJECT_HANDOFF_v1.1.md` §2–3: stable Runtime, Knowledge, Rule, Collector, Storage, and Frontend architecture, and a mature implementation lifecycle (`PROJECT_HANDOFF_v1.1.md` §5). `CAPABILITY_PORTFOLIO_ASSESSMENT.md` surveyed twelve capability candidates against that settled architecture; C1 (`RecommendationStep` presentation) and C2 (this candidate) were the two real, evidenced Category A candidates it found comparably strong on value, differing only in architectural readiness and implementation risk — C1 required no new Rule, C2 does. C1 has since completed (`ENGINEERING_RELEASE_2.0.md`, HEAD `69e33da` at the start of this session). This document is the first artifact produced for C2.

**A correction to `CAPABILITY_PORTFOLIO_ASSESSMENT.md`'s own characterization, found by direct source inspection during this session's Required Analysis, below.** That document states: *"since no Rule ever produces a Finding referencing declared-dependency Evidence, it is never transported or presented anywhere today, by any consumer."* This is not accurate as stated. `EvidencePresenceRule` (`modiq-rules/src/rules/evidence_presence_rule.rs`) fires unconditionally whenever any Evidence exists in the Assessment, and its Finding's `evidence_ids` is built from `evidence.iter().map(Evidence::id).collect()` — every Evidence item in the Assessment, without a category filter. Declared-dependency `XmlInspection` Evidence is therefore already referenced by this Finding, already nested under it in `apps/console`'s `ReportSummary` (`assessment.rs`'s `evidence_ids` lookup), already rendered by `Reviewing.tsx` (including its `"Declared Dependency"` label) when that Finding is expanded, and already present in the flat evidence lists `modiq-cli` and `apps/sandbox` each print or transport unconditionally. This was independently confirmed by running `modiq-cli assess` against a constructed fixture containing a `<dependency>` element during this session (see *Required Analysis: Current State*). The capability's real gap is not visibility — it is that this Evidence is never *specifically interpreted*: no Rule asks any question of its content, and it is indistinguishable, in every Finding that currently references it, from a `notes.txt` file's mere existence. This distinction — reachable-but-uninterpreted, not unreachable — is the accurate premise for everything that follows in this document.

## Required Analysis

### Current State

**Exactly how Declared Dependency Evidence is produced.** `XmlCollector::inspect` (`modiq-collection/src/collection/xml_collector.rs`, lines 137–175), after confirming the manifest is well-formed XML, iterates `document.descendants()` for every node named `dependency`, in document order. For each one, it reads the node's own text content, trims it, and — only if the trimmed text is non-empty — constructs one `Evidence::with_location` item: category `XmlInspection`, description `"modDesc.xml declares dependency: {name}"`, location `"modDesc.xml"`, label `Some("Declared Dependency")`, source `Some("modDesc.xml")`, content `Some(name)`. **An empty or whitespace-only `<dependency>` element is silently skipped — never recorded as Evidence at all** (`if name.is_empty() { continue; }`). This means a malformed-declaration case (an empty `<dependency>` tag) never reaches the Rule Engine as Evidence; no future Rule can interpret a fact Collection never reports. This is a real boundary future Rule design must respect, not a gap this Capability Definition proposes to close (that would be a Collection-Axis change, not an Interpretation-Axis one — see *Architectural Boundaries*).

**Exactly where it enters the pipeline.** `AssessmentService::execute_from_assessment_input` (`modiq-engine/src/engine/assessment_service.rs`, line 139) calls `evidence.extend(XmlCollector.collect(&assessment_input)?)` unconditionally, alongside the routed structural Collector and `RuntimeLogCollector` — confirmed directly, this is Sprint 7's Multi-Source Evidence Collection, unchanged. Every declared-dependency Evidence item becomes part of the Assessment's own `evidence` collection before `RuleEngine::evaluate` is ever called.

**Exactly where it stops.** `RuleEngine::evaluate` (`modiq-rules/src/rules/engine.rs`, lines 50–71) dispatches, in fixed declaration order, to `EvidencePresenceRule`, `StructuralDuplicationRule`, `VersionCompatibilityRule`, then `RuntimeLoadFailureRule`. Checked directly against each:

- `EvidencePresenceRule` — matches unconditionally on any non-empty Evidence set, producing exactly one `Informational` Finding titled `"Evidence collected"` referencing *every* Evidence item's id, declared-dependency items included.
- `StructuralDuplicationRule` — filters for `EvidenceCategory::StructuralDuplication` only; declared-dependency Evidence is category `XmlInspection`, never matched.
- `VersionCompatibilityRule` — filters for `EvidenceCategory::XmlInspection`, then further filters on `item.description().strip_prefix(DECLARED_DESC_VERSION_PREFIX)` (`"modDesc.xml declares descVersion: "`). A declared-dependency item's description begins `"modDesc.xml declares dependency: "` — a different prefix — so `strip_prefix` returns `None` and the item is silently excluded at this second filter stage, confirmed directly by the exact string constants in both `xml_collector.rs` and `version_compatibility_rule.rs`.
- `RuntimeLoadFailureRule` — filters for `EvidenceCategory::RuntimeLogs` only; never reached.

So the accurate statement is: declared-dependency Evidence *is* referenced by a Finding (`EvidencePresenceRule`'s), but by the one Rule whose match condition is "any Evidence exists at all," not by any Rule that asks a question about its content. It stops at the second-stage content filter inside `VersionCompatibilityRule` — the only Rule that inspects `XmlInspection` Evidence's own text — which is looking for a different, unrelated fact (the declared `descVersion`).

**Exactly why it never becomes a content-specific Finding** (it already becomes part of a content-*blind* one — `EvidencePresenceRule`'s, per the correction above). No Rule's second-stage filter recognizes the `"modDesc.xml declares dependency: "` prefix or inspects a declared-dependency item's `content()` field (the raw dependency name, e.g. `"FS25_exampleModOne"`). This is a straightforward absence, not a defect: `VersionCompatibilityRule`'s own doc comment states its purpose narrowly ("Version-aware interpretation begins here... this Rule is the first and only place that value is judged"), and no other Rule was ever written to look at this content. Sprint 8's Architectural Resolution (cited in `version_compatibility_rule.rs`) scoped that Rule to the `descVersion` fact specifically; nothing in the repository's history since has proposed extending it, or any other Rule, to the dependency-declaration fact.

**Exactly why no current consumer specifically observes it (as opposed to generically observing it — see the correction above).** `apps/console`'s `Reviewing.tsx` renders each expanded Finding's own `evidence` list with `evidence.label` bolded, so a declared-dependency item does appear there today, labeled `"Declared Dependency"` — but nested under `"Evidence collected"`, the same generic Finding every other Evidence item in the same Assessment is nested under, with no way for a user to distinguish "this Assessment has a declared dependency worth attention" from "this Assessment has any Evidence whatsoever." `modiq-cli`'s `format_report` (`assess.rs`, lines 71–78) prints the full flat `report.evidence()` list unconditionally, including declared-dependency items, with no Finding-level grouping shown at all (confirmed directly: a real `modiq-cli assess` run against a constructed fixture with one `<dependency>` element produced exactly `Evidence (4)` including the line `[XmlInspection] modDesc.xml declares dependency: FS25_exampleModOne`, and `Findings (1)` — only `EvidencePresenceRule`'s generic Finding). `apps/sandbox`'s `AssessmentSummary`/`EvidenceEntry` likewise carries the full flat evidence list, generically, with no `label` field at all (`EvidenceEntry` has only `id`, `category`, `description`, `location`). `modiq-storage`'s `PersistedEvidence` also carries only `category`, `description`, `location` — no `label`; the declared-dependency fact survives persistence only inside its own description string.

**Summary of the actual gap.** The gap C2 concerns is interpretation, not reachability: declared-dependency Evidence already flows, generically and un-filtered, through Collection → Assessment → the generic `EvidencePresenceRule` Finding → Report → Storage/CLI/Sandbox/Console. What is absent is any Rule that treats a declared dependency's own content as worth a question — the same kind of question `VersionCompatibilityRule` already asks of the declared `descVersion`, `StructuralDuplicationRule` already asks of duplicate archive entries, and `RuntimeLoadFailureRule` already asks of a runtime log line. Declared-dependency Evidence today gets none of that; it gets exactly the same treatment as `notes.txt`'s mere existence.

### User Value

Following this Capability Definition's own instruction to keep these four separate rather than combine them into one score:

- **Repository capability** — real and present. `XmlCollector` already produces the raw fact (confirmed above); the Rule Engine's dispatch model (`GOV-012`) already supports adding a fixed-order, independently-composing Rule without new machinery; `Finding`/`Recommendation` construction, `AssessmentReport::generate`, `PersistedAssessmentReport::from_report`, and every consumer's transport code (console, CLI, sandbox) already handle an arbitrary new Finding generically, with no Rule-specific special-casing anywhere in any of those four call paths (confirmed directly: `report.findings()`/`report.evidence()` are iterated generically in `assess.rs`, `assessment.rs` (console), and `lib.rs` (sandbox); `PersistedAssessmentReport::from_report` iterates `report.findings()` generically). A new Rule's Finding would appear in all four without any change to any of them — the same "zero-touch" property every historical Rule addition (Sprint 5, 8, 11) has already demonstrated for `modiq-report`, and Storage's own architecture (`GOVERNANCE.md`, Storage boundary) makes structurally guaranteed for `modiq-storage` as well.
- **Engineering readiness** — real, with one named caveat. The lifecycle that would carry this forward (Capability Definition → some form of architectural determination → Implementation Authorization → Implementation → Report → Closeout) is demonstrated and current, most recently by C1. The specific caveat: `SPRINT12_ARCHITECTURAL_RESOLUTION.md` §8 names "the Rule Composition question for a second recognized fact within an already-interpreted `EvidenceCategory`" as untested — "no historical instance yet exists." C2 would be exactly that instance: a second Rule matching `XmlInspection` Evidence, alongside `VersionCompatibilityRule`. GOV-012's own Question 3 resolution (Rules compose independently, no suppression) is repository-adopted architecture, not merely guidance — but its own evidence base was two Rules total, neither sharing a category. Whether GOV-012's resolution extends to two Rules sharing one category without further architectural determination is a real, named, currently unresolved question (see *Next Required Repository Artifact*).
- **Implementation cost** — appears low relative to prior Rule additions, based on structural comparison only (this document does not estimate effort or design implementation): no new Collector, no new `EvidenceCategory`, no new crate dependency edge, and a Rule shape (`fn evaluate(&self, evidence: &[Evidence]) -> Option<RuleOutcome>`) already established four times over (`EvidencePresenceRule`, `StructuralDuplicationRule`, `VersionCompatibilityRule`, `RuntimeLoadFailureRule`).
- **User-visible value** — a user who has ever seen a `"Declared Dependency"`-labeled Evidence item nested under the generic `"Evidence collected"` Finding has, in fact, already seen this fact; what they have never seen is a Finding that specifically concerns it — a title, summary, and Mod Health Dimension that names the dependency content as the subject of the platform's own conclusion, the way `"Unrecognized declared version"` does for `descVersion`. `Glossary.md` already names `Dependency` as a defined platform concept ("Any external requirement needed for a mod to function correctly") and `Rule` examples explicitly include `"Missing Dependency"` — a real, specification-named future Rule this capability does not itself deliver: detecting a genuinely *missing* dependency requires knowing whether a declared dependency is actually satisfied elsewhere, which is cross-mod knowledge this capability's own single-mod-scoped foundation does not have access to (see *Explicit Exclusions*). What this capability could ground is narrower and different in kind — a judgment about a declared dependency's own content, using only what one mod's manifest already states — without committing this document to that or any other specific judgment.

## Capability Statement

**The Rule Engine gains the ability to ask a question of a mod's own declared-dependency content — the `XmlInspection` Evidence `XmlCollector` already produces for every declared `<dependency>` element — rather than that content being interpreted only by `EvidencePresenceRule`'s undifferentiated "any Evidence exists" match, indistinguishable there from any other Evidence item in the same Assessment regardless of category or content.**

This statement deliberately does not name what question a new Rule would ask, what Finding it would produce, what severity or Mod Health Dimension it would assign, or whether it would produce a Recommendation — those are Rule-design questions, explicitly out of scope for a Capability Definition (see *Explicit Exclusions*) and left to whatever artifact follows.

## Existing Repository Foundation

- **`XmlCollector`'s declared-dependency production** (`modiq-collection`, Sprint 7) — the raw fact itself, confirmed directly this session (`xml_collector.rs`, lines 153–172): one `XmlInspection` Evidence item per non-empty declared `<dependency>` element, labeled `"Declared Dependency"`, carrying the raw name in `content()`.
- **`VersionCompatibilityRule`'s own two-stage filter pattern** (`modiq-rules`, Sprint 8) — category match (`EvidenceCategory::XmlInspection`), then content-shape match (a specific description prefix, `strip_prefix` + parse) — the exact mechanism `SPRINT12_ARCHITECTURAL_RESOLUTION.md` names as "the two-stage filter pattern every category-specific Rule already uses internally." A Rule interpreting declared-dependency content would need the identical two-stage shape, matching a different, already-fixed prefix (`"modDesc.xml declares dependency: "`) instead of `VersionCompatibilityRule`'s own.
- **`RuleEngine::evaluate`'s fixed-order, independently-composing dispatch model** (GOV-012, Resolved) — a new Rule is added as one more `if let Some(outcome) = NewRule.evaluate(evidence) { outcomes.push(outcome); }` line, per the pattern all four existing Rules already follow; no trait, registry, or dispatch table (ADR-0010, GOV-004).
- **`Evidence`'s Label/Source/Content anatomy** (Engineering Alignment, Initiative 3, Item 4 — Adopted in part; `DataModel.md`) — already populated for every declared-dependency item today (`label: "Declared Dependency"`, `source: "modDesc.xml"`, `content: <the raw name>`), giving a future Rule a structured field to match against beyond the description string alone, exactly as `VersionCompatibilityRule` currently does not need to (it parses `description()` because Sprint 8 predates this anatomy) but a new Rule reasonably could.
- **`Finding`'s existing invariant that it may stand without a Recommendation** (Engineering Alignment, Initiative 3, Item 3 — Adopted; `RuleEngine.md`, Recommendation Generation) — a new Rule need not pair every Finding with a Recommendation, and by extension need not require a new `RepairRecipe` to exist. Confirmed: no `RepairRecipe` for any dependency-related concept exists in `modiq-knowledge` today (only `version_compatibility_declared_version_mismatch`), despite `Glossary.md`'s Repair Recipe entry naming "Dependency installation" as one of five reference kinds and `RepairStepKind::DependencyInstallation` already existing as a variant in `modiq-knowledge/src/knowledge/repair_recipe.rs` — real, unused (zero-consumer) scaffolding for exactly this kind of future content.
- **The transport-genericity already demonstrated by every consumer** (see *Repository Context*'s correction and *User Value*'s repository-capability finding) — `modiq-report`, `modiq-storage`, `modiq-cli`, `apps/console`, and `apps/sandbox` all iterate `Finding`/`Evidence` generically; none requires modification to carry a new Rule's output.

## Existing Architectural Principles

- **ADR-0007 (Runtime Entity Design Pattern).** Any new `Finding`/`Recommendation` this capability might eventually produce would follow the same infallible-construction, no-mutation-method, freshly-assigned-identity pattern every Runtime entity already follows — nothing new to establish.
- **`RuleEngine.md`'s Evidence-Based execution principle.** "Rules never operate on assumptions or unsupported observations... every conclusion should be supported by collected Evidence" — directly relevant, since the only Evidence currently available about a declared dependency is the name itself (and its repetition, or lack of it, within one manifest); no Evidence exists today about whether a declared dependency actually resolves elsewhere (see *Explicit Exclusions*, cross-mod resolution).
- **`DataModel.md`'s Finding Severity definitions** — a future Rule "must never assign a severity stronger than what its Evidence conclusively establishes." Declared-dependency Evidence, as currently collected, establishes only what a manifest *declares*, never whether that declaration is satisfied — a structural constraint on what severity a future Rule could honestly assign, not a decision this document makes.
- **GOV-012's Rule composition resolution (Resolved)** — Rules compose independently; no suppression model. Directly relevant and, per *User Value*'s engineering-readiness finding above, not yet tested against two Rules sharing one `EvidenceCategory`.
- **`FrontendArchitecture.md`'s Presentation Without Inference / Explainable Continuity** — unaffected by this capability at the Capability Definition stage; relevant only once, and if, a presentation-layer follow-on capability (mirroring C1's own shape) is separately considered. Not addressed here (see *Architectural Boundaries*).

## Existing Repository Patterns

- **The Interpretation Axis's judgment test** (`SPRINT12_ARCHITECTURAL_RESOLUTION.md` §5, §8) — "does interpreting the fact require a judgment... no existing Rule already makes?" A Rule that asks whether a declared dependency name is, for example, duplicated within one manifest would be a *new* judgment (no existing Rule asks any question of declared-dependency content), landing this candidate as an Interpretation-Axis **Expansion** (a new, sibling Rule using the established two-stage filter) — structurally, not a Collection-Axis or Evidence-Axis event at all, since no new Collector and no new `EvidenceCategory` is implicated. This classification is offered as a direct, structural reading of the existing procedure against today's evidence, consistent with `PROJECT_HANDOFF_v1.1.md` §5's statement that Capability Identity classification precedes Capability Definition — it is not a re-performance of that procedure, and it does not resolve the "second Rule, same category" gap named above.
- **The Duplicate-detection precedent, precisely located.** `ArchiveCollector`'s duplicate-entry detection (GOV-011) is a **Collection-layer** precedent: `detect_duplicate_entry_names` compares entries against each other during Collection and synthesizes one new, distinct `StructuralDuplication` Evidence item recording that fact. `StructuralDuplicationRule` itself performs no comparison of its own — it only filters Evidence by category, consuming a fact Collection already established. **No existing Rule in this repository compares multiple Evidence items against each other** — every existing Rule's `evaluate` filters or maps over Evidence independently, item by item (confirmed directly against all four Rules). `XmlCollector` performs no equivalent synthesis for declared dependencies today — confirmed directly: a manifest declaring the same dependency name twice produces two separate, undeduplicated Evidence items, with no "duplicate detected" fact recorded anywhere. Named here only to locate the actual precedent correctly, not as a design decision that a future Rule for declared dependencies should ask this or any specific question; that remains open.
- **The "malformed/absent input recorded as Evidence, not silently dropped" convention** (`XmlCollector`'s `absent_manifest_evidence`/`malformed_manifest_evidence`) — contrasted directly against declared-dependency collection's own, different choice: an empty `<dependency>` element is dropped entirely, not recorded (see *Current State*). This is an existing, asymmetric fact about today's Collection layer that any future Rule design must account for, not something this document proposes to reconcile.

## Architectural Boundaries

The following must remain unchanged by this capability, as a direct consequence of already-adopted architecture, confirmed directly against current source:

- **The Collector Contract and `XmlCollector` itself.** This capability is Interpretation-Axis only. `XmlCollector` already produces the Evidence in full; nothing about this capability requires any change to Collection (`EvidenceCollection.md`; `GOVERNANCE.md`, Evidence Collection boundary: "must never evaluate Evidence, or produce Findings or Recommendations").
- **`EvidenceCategory`'s closed set.** Declared-dependency Evidence remains `XmlInspection`; this capability does not activate the dormant `DependencyResolution` variant (unrelated — see *Explicit Exclusions*) or introduce a new category.
- **`RuleEngine::evaluate`'s dispatch shape.** Any new Rule is one more fixed-order `if let` dispatch line — no trait, registry, or plugin mechanism (ADR-0010, GOV-004, GOV-012).
- **The Runtime/Knowledge boundary.** Whether a `RepairRecipe` accompanies any resulting Finding is undecided and, per Initiative 3 Item 3, not required; this document does not touch `modiq-knowledge`.
- **`modiq-report`, `modiq-storage`, `modiq-cli`, `apps/console`, `apps/sandbox`.** Confirmed directly (see *Existing Repository Foundation*): all five already handle an arbitrary new Finding/Evidence generically. This capability, at the Capability Definition stage, implicates none of them.
- **Console's Frontend Architecture boundary (`FrontendArchitecture.md`).** Unaffected — a new Finding flows through `Reviewing.tsx`'s existing generic Finding-rendering with no code change, exactly as every historical Rule addition has already demonstrated for the CLI and Sandbox equivalents. Whether `Reviewing.tsx` should ever distinguish this new Finding's presentation from any other is explicitly not addressed here (see *Explicit Exclusions*).
- **GOV-013 (FindingSeverity Severity/Kind Conflation, Open by design).** Not reopened by this document. A future Rule's severity assignment (e.g., whether a duplicate declared dependency is `Warning` or `BestPractice`) is a live instance of the tension GOV-013 already names, not a new one — recorded here as relevant context, not resolved.

## Explicit Exclusions

Intentionally outside this capability's own scope:

- **Any Rust type, Rule matching logic, prefix string, severity assignment, Mod Health Dimension assignment, or Recommendation/RepairRecipe design.** This document names that a Rule-shaped gap exists; it does not design the Rule.
- **Cross-mod dependency resolution** — whether a declared dependency actually exists in an installation, requiring Evidence about mods other than the single Assessment Subject. This is `CAPABILITY_PORTFOLIO_ASSESSMENT.md`'s own separate candidate C5, named there as Category B, blocked on its own undesigned mechanism (`STORAGE_ARCHITECTURE_EVALUATION.md`'s "cross-mod collection validation"). Nothing available to a Rule today — confirmed directly, `AssessmentSubject` is a zero-field unit struct (`subject.rs`) carrying no identifying content, and no Evidence records any fact about a second mod — makes cross-mod resolution reachable from this capability's own foundation.
- **Activating `DependencyResolution`** (the dormant `EvidenceCategory` variant) or any other dormant category. Unrelated: declared-dependency Evidence is, and would remain, `XmlInspection`.
- **Any change to `XmlCollector`, including recording currently-dropped empty `<dependency>` declarations as Evidence.** A Collection-Axis change, not an Interpretation-Axis one; named as a boundary in *Current State*, not proposed here.
- **Any presentation, visual, or interaction treatment in `apps/console`, `modiq-cli`, or `apps/sandbox`** distinguishing this capability's eventual Finding from any other. Mirrors C1's own precedent of treating presentation as a separate, later capability once Runtime content exists to present (`C1_IMPLEMENTATION_REPORT.md`) — here, generic presentation of any new Finding already exists and needs no change to be reachable; a dedicated, distinguishing presentation is a separate future question, not this one.
- **Resolving GOV-013** or reopening `FindingSeverity`'s model.
- **`C1`'s own remaining deferred items** (`apps/sandbox`/`modiq-cli` parity for `RecommendationStep`), **`C6` (Confidence), or any other Capability Portfolio Assessment candidate.**

## Capability Success Criteria

Declared-dependency Evidence's content is the subject of at least one Rule's own judgment: a Finding exists whose title, summary, and evidence references are specifically about a mod's declared dependency content — not merely a member of `EvidencePresenceRule`'s undifferentiated "any Evidence exists" Finding — produced through the same fixed-order, independently-composing Rule dispatch every existing Rule already uses, with no change to `XmlCollector`, `EvidenceCategory`, or any consumer's transport code required for that Finding to be reachable.

---

## What Success Does Not Require

- It does not require cross-mod dependency resolution, or any judgment about whether a declared dependency actually exists anywhere outside the Assessment Subject's own manifest.
- It does not require every mod's manifest to declare a dependency, or every Assessment to produce this new Finding — an Assessment Subject with no declared dependencies, or with only declarations the new Rule's own (undecided) judgment finds nothing worth concluding about, is a valid, expected outcome, not a gap to fill (mirroring `VersionCompatibilityRule`'s and `RuntimeLoadFailureRule`'s own precedent of returning `None`).
- It does not require a `RepairRecipe` or a Recommendation to accompany the new Finding (Initiative 3, Item 3).
- It does not require activating `DependencyResolution` or any other dormant `EvidenceCategory`.
- It does not require any change to `apps/console`, `modiq-cli`, or `apps/sandbox` — generic presentation of the resulting Finding is already reachable through each, confirmed directly this session.
- It does not require resolving GOV-013, GOV-012's untested "second Rule, same category" question in the abstract, or any other Governance Register item — only, as `GOVERNANCE.md`'s own Purpose already states generally ("Implementation must never silently redefine the architecture"), that a genuine architectural question, once named, not be carried silently into implementation.

## Next Required Repository Artifact

Determined fresh, against this capability's own evidence — not against C1's conclusion, which turned on a different, already-Adopted governing principle (`FrontendArchitecture.md`'s Consumer-Owned State) that has no analogue here.

This Capability Definition's own Required Analysis surfaced one concrete, named, unresolved architectural question that a Rule-shaped capability requires answering before implementation, and that no existing Adopted determination already, non-discretionarily, settles:

**Does GOV-012's Rule Composition resolution (Rules compose independently; no suppression) extend, without further architectural work, to two Rules that each interpret the same `EvidenceCategory` — one already existing (`VersionCompatibilityRule`, on `XmlInspection`), one newly proposed (this capability, also on `XmlInspection`)?** `SPRINT12_ARCHITECTURAL_RESOLUTION.md` §8 names this exact case directly and states plainly that no historical instance yet tests it: *"no historical decision has yet tested two Rules, or two recognized fact-shapes, sharing one already-interpreted `EvidenceCategory`... a disciplined extrapolation of the two-stage filter pattern... not a fifth confirmed data point."* This is not a hypothetical concern manufactured for this document — it is a gap the repository's own architecture-reconciliation process already identified and left explicitly open, and this capability is the first concrete candidate to actually reach it.

This differs in kind from C1's own path. C1 matched an already-Adopted principle "by construction" (`PROCESS_DETERMINATION_C1_RECOMMENDATION_STEP_PRESENTATION.md`'s own Prong 1) and proceeded directly to an Implementation Authorization on that basis. C2 instead surfaces a question no Adopted determination has yet answered — the repository's own words are "strong guidance, not settled precedent." Per `GOVERNANCE.md`'s Architectural Review Process and this project's own standing discipline (`PROJECT_HANDOFF_v1.1.md` §6, Principle 2: "a concrete forcing function, not a hypothetical one, justifies a model change... the reverse"), a real forcing function — this capability — is now the concrete instance that question needed. A Process Determination's own role (`PROCESS_DETERMINATION_C1_RECOMMENDATION_STEP_PRESENTATION.md`'s own Purpose) is to establish, by comparing precedent, whether a genuinely open design question exists at all; here that question is already answered, directly and in the repository's own words, by `SPRINT12_ARCHITECTURAL_RESOLUTION.md` §8 itself. **The repository-supported next artifact is therefore an Architecture Evaluation**, closing the "second Rule, same category" gap on its own, general terms, reusable by any future capability that reaches it — not a Process Determination, whose own threshold question this capability's Required Analysis has already answered.
