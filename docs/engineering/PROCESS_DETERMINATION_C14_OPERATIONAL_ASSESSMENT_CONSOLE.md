## 3. Process Determination Method

This document applies the same reusable two-prong test C1, C3, and C4 each applied (and that C12 applied and failed), per those documents' own stated instruction that the test is reusable, not reinvented each time:

1. **Prong 1** — Is there a genuinely open architectural design question, or is the governing principle already Adopted / does existing architecture already settle the matter?
2. **Prong 2** — Is any alternative architectural approach actually being weighed?

Both prongs must resolve in favor of "no open question, no alternative" for the next artifact to be an Implementation Authorization. If either prong fails, repository precedent (C2, C12) is to proceed to Architecture Evaluation first. Precedent is treated here as evidence of how the test has been applied before, not as a rule dictating C14's own outcome in advance — each of the six questions below is independently investigated against current source.

## 4. Investigation of the Six Named Questions

### Question 1 — Does ZIP selection require any new boundary or transport mechanism?

**Finding: no.** `AssessmentService::execute_from_assessment_input` already performs archive-vs-filesystem routing entirely internally, before any Evidence exists, using only the input path string it already receives. The Tauri command already accepts that string with no shape constraint. Nothing about *how* the console obtains that string (folder dialog vs. filtered file dialog) crosses, weakens, or adds a new mode to the Engine/Consumer boundary `FrontendArchitecture.md` establishes — both are plain string values produced entirely on the presentation side, before any request is made. No new transport field, no new command, no new response shape is implicated by either intake shape.

### Question 2 — Does repeated independent assessment execution require any Runtime lifecycle change?

**Finding: no.** §2's re-verification of `separate_executions_are_independent_and_deterministic` confirms this mechanism already exists, is already tested, and requires no `Assessment` to be reopened — each call constructs its own fresh `Assessment` via `Assessment::new` inside `AssessmentService::execute`. `INV-012` is not implicated because no `Assessment` value is asked to accept a second lifecycle transition; a second, independent value is created instead. This is the precise distinction §3 of the Capability Definition draws, and re-reading `INV-012`'s own text directly (§2, above) confirms the invariant's scope does not reach this case at all — there is no tension to resolve, adopted or otherwise.

### Question 3 — Does resetting `Workspace.tsx` local state have any architectural consequence?

**Finding: no.** `report`/`selectedPath`/`status`/`error` are, and remain, local `useState` values with no persistence, no Runtime binding, and no Tauri round-trip of their own. Resetting them is exactly the same class of operation `Console.tsx`'s own `signOut` already performs today (§2) — an already-shipped precedent for "reset local presentation state, return to an earlier screen" that introduced no Architecture Evaluation, ADR, or governance item when it was built, and needed none. No governing document treats workspace-level UI state as an architectural concern; `FrontendArchitecture.md`'s Boundary Enforcement concerns evaluative inference over engine output, not the lifecycle of local view state holding a `ReportSummary` the engine already fully computed.

### Question 4 — Could "assess another mod" accidentally implicate Initiative 2?

**Finding: not if scoped as this Capability Definition scopes it, and the distinction survives direct re-reading of Initiative 2's own governing text.** `INITIATIVE_2_ARCHITECTURAL_RESOLUTION.md` §2 states its Central Architectural Question entirely in terms of one `Assessment`/Report continuing to reflect new material after completion — "Submitting more material doesn't produce a second Report or a new version of one; it continues updating the same Report" (quoting `THE_ASSESSMENT_REPORT.md` §2, as reproduced there). C14's "assess another mod" does the opposite of what that sentence describes: it produces a **second, unrelated** Assessment Subject's own Report, through a **second, independent** `execute_from_assessment_input` call, with no reference — data, identity, or otherwise — back to the first. Nothing in Initiative 2's Evaluation or Resolution discusses, names, or leaves open any question about a user choosing to assess an unrelated second Subject; its entire scope, confirmed by direct re-reading in §2 above, is same-Subject supplementation. The risk named is real only as an *implementation-discipline* risk (§9, below), not as a substantive overlap in subject matter.

### Question 5 — Is the existing Tauri dialog capability sufficient?

**Finding: yes, confirmed directly this session (§2), more conclusively than the Capability Definition itself claimed.** `dialog:default` grants `allow-open` at the command level, without parameter-level scoping; the same grant already exercised for `directory: true` already covers `directory: false` with `filters`. No capability-file change is required at all — narrower than the Capability Definition's own "conditional participation... only if real-machine testing shows" framing, which this document does not need to override, only sharpen: the condition already resolves in favor of "not required," pending only the ordinary confirmation that comes from actually running the app (Implementation Planning's own concern, not this document's).

### Question 6 — Are any DTO or command changes actually necessary?

**Finding: no.** Re-confirmed directly in §2: `submit_assessment(input_path: String) -> Result<ReportSummary, String>` and every struct in `ReportSummary`'s own graph (`FindingSummary`, `EvidenceSummary`, `RecommendationSummary`, `RecommendationStepSummary`) are unaffected by which of two path strings is supplied, or by how many times the command is called in one console session. No field, variant, or command parameter needs to exist that does not already exist.

## 5. Applying the Two-Prong Test to C14

**Prong 1 — is there a genuinely open design question, or does existing architecture already settle the matter?**

No genuinely open design question survives investigation. Each of the six questions above resolves to an already-implemented, already-tested mechanism, an already-shipped precedent for the one novel-seeming behavior (local state reset, via `signOut`), or a governing document (`INV-012`, `FrontendArchitecture.md`) whose own text, re-read directly, does not reach the case C14 proposes. This differs from C12's own Prong 1 failure in a specific, checkable way: C12 failed because no Adopted principle existed for the actual mechanism it needed (schema evolution with read-compatibility) — the absence itself was the problem. C14 has the opposite shape: the mechanisms it needs (archive routing, independent repeated execution, an unscoped dialog `open` permission) do not merely have an absence of contrary principle — they are already built, shipped, and passing tests today.

**Prong 2 — is any alternative architectural approach actually being weighed?**

No. C14 proposes no new dispatch mechanism, no new crate-boundary crossing, no new command, and no reinterpretation of any existing boundary. There is no design fork analogous to C4's flat-vs-nested transport question or C12's schema-evolution alternatives (§6 of `PROCESS_DETERMINATION_C12...md`) — the two behaviors in scope each have exactly one available implementation shape given everything already built: call `submitAssessment` with whichever path string the user selected, and reset four local state variables to their initial values. Neither admits a genuine alternative at the architectural level; whatever variation exists (e.g., one combined chooser vs. two separate affordances) is a UI-composition choice within `Workspace.tsx`, not a competing architecture.

## 6. Determination

**C14 matches C1's, C3's, and C4's path on both prongs of the test.** No genuinely open design question exists among the six named questions — each resolves to already-implemented, already-tested mechanism or an already-established, directly analogous local-state-reset precedent in this same codebase. No alternative architectural approach is being weighed.

**The next required repository artifact is an Implementation Authorization**, not an Architecture Evaluation or Architectural Resolution.

This confirms, rather than merely repeats, the Capability Definition's own §7 preliminary conclusion — every fact that conclusion rested on was re-verified fresh against current source in §2, and one of them (dialog permission scope) was found to resolve more favorably than originally stated, not less.

## 7. What Should Follow If Implementation Authorization Is Granted

Named here for continuity into the next lifecycle stage; **not decided, designed, or authorized by this document**:

- **Implementation Authorization** should bound participating files exactly as the Capability Definition's §14 Repository Impact already states: required participation limited to `apps/console/src/workspace/Workspace.tsx`; conditional participation in `apps/console/src-tauri/capabilities/default.json` now understood (§2, §4 Q5) to be unlikely to be needed in practice, confirmed only by running the app; `Reviewing.tsx` limited strictly to the doc-comment correction, with no behavioral change, exactly as the Capability Definition's approved wording states.
- **Implementation Plan**, if the Authorization calls for one, should sequence: (1) the second intake affordance, verified first against a real `.zip` on this machine; (2) the "Assess another mod" reset affordance, verified second against a real second mod of a different shape (directory after zip, or vice versa) to directly exercise Success Criterion 4 (no stale state); (3) the `Reviewing.tsx` comment correction, made last, once the return affordance exists and the comment's current claim is actually false.
- **Testing/verification** should follow the C13 precedent exactly, per the Capability Definition §13: `cargo fmt --check`, `cargo check --workspace`, `cargo test --workspace`, `apps/console`'s `tsc && vite build`, and manual real-I/O verification — a real extracted directory, a real `.zip` (this machine's own FS25 mods folder already contains two: `FS25_HH_HempProdSystem.zip`, `Hashy_01Silv.zip`), and the full Assess → Review → "Assess another mod" → Assess-a-different-mod cycle exercised by hand, confirming the second report carries no residue of the first. No frontend test framework should be introduced solely for this capability.
- No Rust-side test is anticipated to be strictly required (`AssessmentService`'s own suite already covers archive routing and execution independence at the engine layer) — but Implementation Planning may still choose to add one or two thin `assessment.rs`-level tests mirroring its existing fixture-directory tests against a bundled `.zip` fixture, purely for regression coverage at the Tauri-command layer, not because a gap in engine-level coverage exists.
