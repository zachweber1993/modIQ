## §3 — Architectural Reasoning

Reasoning only; no decision is stated in this section.

**On whether GOV-012 already governs shared-category composition.** GOV-012 Question 3's resolution establishes one architectural fact about dispatch: every Rule is evaluated against the full Evidence set, independently, with no suppression, regardless of overlap with any other Rule's own match. This fact is directly demonstrated, not merely asserted, by `RuleEngine::evaluate`'s own code (§2): the dispatch mechanism has no concept of category ownership to enforce a limit with, even if GOV-012 had wanted one. GOV-012's own illustrative grounding — generic Rule plus one specific Rule — under-represents the resolution's own textual scope, which contains no cardinality qualifier. Reading GOV-012's own general text as controlling over its own narrower illustration is an interpretive choice this Resolution makes explicitly, not a fact GOV-012's own drafting settles unambiguously on its face — recorded here as an adopted interpretation, not claimed as the only textually possible one. The Evaluation's Reading A (a mechanical/structural composition risk) was checked directly against the dispatch code and found unsupported. Nothing found this session changes that finding. **The composition/dispatch question is not a gap in GOV-012; it is a question about how completely GOV-012's own already-general text is read, which this Resolution now settles by adopting the broader reading.**

**On why `PROJECT_STATUS.md`'s record, not the two source documents' own unsynchronized status text, governs.** `SPRINT12.md` and `SPRINT12_ARCHITECTURAL_RESOLUTION.md` both still read "Proposed... awaiting Chief Architect approval" in their own headers (§2), never updated. `PROJECT_STATUS.md`'s direct, unqualified "Sprint 12 — Complete" record is treated as authoritative on this narrow factual question because it is the repository's own living status document, purpose-built to track exactly this kind of closeout fact, and because every other repository document written since Sprint 12 (`PROJECT_HANDOFF_v1.1.md`'s own Sprint History table, the Capability Portfolio Assessment, C1's full lineage, this capability's own Capability Definition and Architecture Evaluation) treats Sprint 12 as settled without qualification. The two source documents' own unsynchronized status text is accordingly read as a documentation-currency gap, not a live approval question — consistent with this repository's own recorded tolerance for the identical pattern elsewhere.

**On what Sprint 12's caveat is actually about, confirmed against this session's own re-reading of both `SPRINT12.md` and `SPRINT12_ARCHITECTURAL_RESOLUTION.md`.** Both documents name the same gap in the same terms and neither, anywhere, frames it as a dispatch-mechanism concern — both frame it as an evidentiary-confidence concern about the **two-stage filter pattern's own internal correctness** once two category-specific Rules share a category: `SPRINT12.md` §8.2 calls it "an extrapolation of the two-stage filter pattern... an extrapolation, not a fifth independent data point." This confirms the Evaluation's Reading B rather than Reading A: the real, previously-unarticulated precondition is that two category-specific Rules' own content-shape filters (each Rule's second matching stage) must not both claim the same Evidence item, or their respective conclusions cease to be independently trustworthy in the way Explainability requires — not because the *dispatch* would misbehave (it would not), but because a single fact would then support two Rule-authored, potentially divergent claims about itself with nothing in the architecture ever having required either author to check for that.

**On why this precondition was never previously stated.** Every category-specific Rule to date (`StructuralDuplicationRule`, `VersionCompatibilityRule`, `RuntimeLoadFailureRule`) has been its category's only interpreter — confirmed again this session against all four Rule files. Disjointness among content-shape filters was therefore a structural impossibility to violate, not a property anyone verified. This is precisely the shape of gap `RuleEngine.md`'s own Initiative 1 amendments (AC-2, AC-4) were used to close before: an already-true, already-necessary property of correct behavior, made explicit in the architecture text only once a capability arrived that could make it stop holding automatically.

**On whether closing this gap requires new machinery.** No evidence supports that it does. GOV-012's own text already forecloses "a precedence/suppression mechanism," `SPRINT12.md` §6 forecloses "any runtime classification mechanism," and ADR-0010/GOV-004 foreclose any trait, registry, or dispatch table. A disjointness expectation is satisfiable entirely by Rule *authorship* discipline — how a future Rule's own content-shape filter is written — never by a new runtime check, coordinator, or validation layer. Stating the expectation explicitly, as architecture text, is sufficient; enforcing it mechanically is neither required by any evidence reviewed nor consistent with this repository's own repeated "capability before abstraction" discipline.

**On whether the gap is fully closed by stating the expectation, or whether an empirical step remains.** `SPRINT12.md` §11 and `SPRINT12_ARCHITECTURAL_RESOLUTION.md` §10 both treat their own Historical Validation table as validated only against real, shipped decisions — never a hypothetical one. Stating the disjointness expectation now closes the *architectural* question (what must be true); it does not, and cannot, retroactively supply a fifth confirmed historical data point for Sprint 12's own table, which requires an actual shipped Rule to inspect. That confirmation remains a real, future, small step — distinct from, and not blocking, the architectural question this Resolution exists to close.

## §5 — Adopted Decision

**Decision 1 — GOV-012 is interpreted and adopted as already, fully governing Rule dispatch and composition for a shared `EvidenceCategory`.** No amendment to GOV-012's own text is required. `RuleEngine::evaluate`'s existing dispatch mechanism (§2, §3) requires no change to accommodate a second `XmlInspection`-interpreting Rule, or any future Rule sharing any other category. This closes the *composition/dispatch* half of Sprint 12's own caveat.

**Decision 2 — Adopted Architectural Constraint: Rule Conclusion Non-Contradiction.** Stated precisely, in the vocabulary this repository's own Architectural Resolutions already use for this shape of finding (`RuleEngine.md`'s Initiative 1, AC-2/AC-4 precedent; `INITIATIVE_3_ARCHITECTURAL_RESOLUTION.md`'s own Adopted Architectural Constraint entries), and narrowed relative to Alternative B's own originally-proposed scope (§4):

> **When two or more Rules independently interpret the same `EvidenceCategory`, no single Evidence item may support mutually contradictory specific conclusions from two different Rules.** Genuinely independent, non-contradictory conclusions about the same Evidence item — two different, both-true observations a Rule's author did not need to reconcile with any other Rule's own judgment — are not barred by this constraint; only conclusions that could not both be correct are. Where a future Rule's own content-shape match (the second stage of the two-stage filter pattern — `EvidenceCategory` match, then content-shape match — the mechanism every category-specific Rule to date happens to use internally, not a mechanism this constraint mandates) would cause the same Evidence item to satisfy more than one category-specific Rule's own specific judgment, the author of the new Rule SHALL verify the resulting conclusions are not contradictory.
>
> This constrains Rule *authorship*, not Rule *dispatch*. `RuleEngine::evaluate`'s independently-composing, no-suppression dispatch model (GOV-012) is unchanged and remains the correct and sufficient mechanism. Satisfying this constraint is a design-time responsibility of whoever authors a new category-specific Rule; it introduces no runtime check, registry, coordinator, or dispatch-layer validation, consistent with ADR-0010, GOV-004, and `SPRINT12.md` §6's own prohibition on encoding architectural judgment as a runtime mechanism. Verifying non-contradiction requires reading every existing sibling Rule already interpreting that category — no repository mechanism currently performs, or reminds an author to perform, this check; `docs/governance/CodeReviewChecklist.md` was checked directly (§2) and names no such step. Naming this gap, not building a mechanism to close it, is what this Decision does.

**This Decision directly answers a question the Architecture Evaluation itself left open, not previously settled elsewhere.** `C2_ARCHITECTURE_EVALUATION_DECLARED_DEPENDENCY_INTERPRETATION.md` §8 named, as its first Unresolved Risk, whether overlapping specific conclusions from two Rules would violate `RuleEngine.md`'s Explainability principle, or would merely be two legitimate, separately-traceable conclusions — stating plainly that "no repository document currently answers this." This Resolution now answers it: overlap alone does not violate Explainability; only *contradictory* overlapping conclusions would, since two independently true, non-contradictory conclusions about one fact are each still individually well-explained and traceable to their own Rule. Decision 2 is scoped to the contradictory case only, above, for exactly this reason — a broader, all-overlap prohibition would not be justified by the Explainability rationale that supports this narrower one. The Evaluation's own §8 fifth-named risk — that Reading B was "an engineering inference... a hypothesis to check, not as settled" — is also resolved here: this Resolution adopts the narrowed version of that inference, above, as settled architecture, not merely as a hypothesis, for the reasons stated in this paragraph and in §3.

This closes the *content-shape correctness* half of Sprint 12's own caveat, at the architectural level. It does not, by itself, design, name, or constrain any specific future Rule's own prefix, matching logic, or content — that remains, exactly as before, Implementation Planning's responsibility, out of scope here.

**Decision 3 — Sprint 12's "genuinely untested" caveat is resolved architecturally; its empirical confirmation is deferred, not blocking.** The caveat's dispatch-mechanism reading (Reading A) was already unsupported and remains so. Its content-shape reading (Reading B) is closed by Decision 2's Constraint. What is **not** resolved by this document, and is not claimed to be: `SPRINT12.md`'s and `SPRINT12_ARCHITECTURAL_RESOLUTION.md`'s own Historical Validation tables still contain zero real, shipped instances of two category-specific Rules sharing one category. That remains true until a real Rule exists to inspect against Decision 2's Constraint. This Resolution establishes that such inspection, once available, is what closes the empirical gap — not a precondition to be discharged before a second Rule may be authored or implemented (Alternative C, adopted in full, §4). That inspection may confirm Decision 2's Constraint as adequate exactly as adopted, or it may instead demonstrate — against a real, examined Rule, not in the abstract — that the Constraint, or the Explainability reasoning behind it (§5, Decision 2), requires correction. Alternative C's own original text named both outcomes explicitly; this Resolution adopts Alternative C in that full form, not only its confirming branch, and does not treat Decision 2 as immune from revision once a real instance exists to check it against.

**Decision 4 — No further architectural principle beyond Decision 2 is required.** Checked against `RuleEngine.md`'s six responsibilities and Execution Principles, `Architecture.md`'s System Overview, `DataModel.md`'s Finding Severity section, and `KnowledgeModel.md` (all re-confirmed, §2): none names, or requires resolving, any question beyond Rule conclusion non-contradiction for this capability shape. Severity/Mod Health Dimension cross-Rule consistency (named as an adjacent, unaddressed risk by the Evaluation's §8) is confirmed, again, to be a distinct question this Resolution does not reach — no evidence connects it to the composition question actually asked here.

## §6 — Direct Answers to the Determinations This Resolution Was Charged to Make

- **Does GOV-012 already govern multiple Rule interpretations of one `EvidenceCategory`?** Yes — this Resolution interprets and adopts GOV-012's own general text as already governing this case (Decision 1), rather than leaving it as an untested extrapolation.
- **Is Sprint 12's "shared `EvidenceCategory`" caveat now resolved?** Architecturally, yes (Decisions 1–2), including the Architecture Evaluation's own previously-open Explainability question (Decision 2). Empirically — a real, shipped confirming *or correcting* instance for Sprint 12's own Historical Validation table — no, and this Resolution does not claim otherwise (Decision 3); that step is named, deferred, and non-blocking, and may revise Decision 2 rather than merely confirm it.
- **Must any architectural principle be adopted, clarified, or amended?** Adopted: the Rule Conclusion Non-Contradiction Constraint (Decision 2, narrower than the disjointness expectation Alternative B originally proposed). Clarified: GOV-012's own scope, interpreted and adopted as already covering shared categories (Decision 1). Amended: nothing — no existing document's substantive text is changed by this Resolution.
- **Does any Architecture document require amendment?** `RuleEngine.md` — a small, targeted future amendment is recommended (§7), mirroring its own existing Initiative 1 AC-2/AC-4 citation pattern, to record Decision 2 as architecture text. Not performed by this document. `Architecture.md`, `DataModel.md`, `KnowledgeModel.md`, `EvidenceCollection.md` — no amendment indicated by any evidence reviewed.
- **Does any Governance Register item require update?** No new Governance Register item is required — this question is closed by this dedicated Resolution, consistent with this repository's own precedent of resolving capability-scoped architectural questions without a permanent Register entry (`docs/governance/PROJECT_STATUS.md`: "every capability shipped in that span either applied and extended already-approved architecture, or... resolved it as its own dedicated Architecture Evaluation without requiring a permanent Register entry"). A pre-existing, unrelated documentation-currency gap is named for completeness, not created by this Resolution: GOV-012's own entry in `GOVERNANCE.md` has never cross-referenced Sprint 12's own elaboration of it; recommended, not performed, that a future housekeeping pass add a citation to this Resolution alongside it.
- **Do any implementation constraints become mandatory?** Yes — Decision 2's Constraint is mandatory for any future category-specific Rule sharing an already-interpreted `EvidenceCategory`, including whatever Rule eventually implements C2. How any specific Rule satisfies it (its own prefix, its own content-shape match) is not decided here.
- **Is any repository precedent established?** Yes, three: (1) GOV-012's independent-composition model is interpreted and adopted here as extending to shared-category Rules — a reusable interpretation for any future capability reaching the same question, subject to that capability's own confirmation that its facts genuinely match, consistent with how this repository has consistently re-derived, not silently assumed, applicability even against strong existing precedent (`C1`'s own Process Determination, this capability's own full Definition → Evaluation → Resolution chain). (2) The two-stage filter pattern now carries an explicit, citable non-contradiction precondition, narrower than blanket disjointness, rather than an implicit, previously-unviolatable one. (3) A defined mechanism for closing a Sprint-12-style "named, untested caveat" is established — retrospective confirmation *or correction* against a real, shipped instance, cited back to the resolving document, not prospective certainty-manufacturing — available as precedent for any future gap of this shape.
